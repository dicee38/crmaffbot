# ТЗ: CRM-бот для отдела продаж

Версия: v0.2 (черновик, актуализируется по ходу разработки)
Дата: 05.09.2026 — ревизия по образцу «Jarvis Fin ERP» (см. §11)
Стек: Python · aiogram 3 · FastAPI · PostgreSQL · Railway

Telegram-бот (Mini App), ведущий учёт действий МОП по воронке (регистрация → депозиты → повторные депозиты), рейтинг менеджеров по эффективности и статистику из нескольких партнёрских программ одновременно — с разграничением доступа по ролям.

**v0.2 — что изменилось:** модель данных обобщена с «депозитов» до «действий МОП» (регистрация/первый депозит/повторный депозит/лид), добавлены каналы/группы каналов/партнёрские платформы как самостоятельные сущности, лидерборды с несколькими метриками, конструктор отчётов и роль «Аналитик». Мульти-проектность (несколько изолированных организаций на один Telegram-аккаунт, см. скриншоты источника) сознательно отложена — см. §11.5.

---

## 1. Назначение и цели

Сейчас результаты менеджеров отдела продаж — депозиты клиентов и данные из партнёрской программы — разрознены и не сведены в одну систему. Нет единого рейтинга сотрудников, руководителю сложно оперативно увидеть, кто выполняет план, а сверка данных из партнёрки с результатами конкретного менеджера делается вручную.

Цель проекта — Telegram-бот, выполняющий роль лёгкой CRM: он собирает депозиты (вручную и автоматически из партнёрки), считает статистику и рейтинг сотрудников, разграничивает доступ по ролям и даёт руководству прозрачную картину без отдельной веб-панели для базовых задач.

Цели:
- Единая база депозитов и статистики менеджеров вместо разрозненных источников.
- Автоматический рейтинг сотрудников за гибкие периоды — день, неделя, месяц.
- Подключение статистики партнёрской программы без ручной сверки.
- Разграничение доступа по ролям: менеджер, тимлид, админ, собственник.
- Архитектура, которую можно масштабировать на несколько команд или организаций без переделки ядра.

## 2. Термины и определения

| Термин | Определение |
|---|---|
| МОП | Менеджер отдела продаж — используемое в интерфейсе название роли «Менеджер» (см. §3). |
| Действие МОП | Единичное событие воронки, которое вносит или получает из партнёрки менеджер: регистрация, первый депозит (FD), повторный депозит (RD) или лид. Депозит (v0.1) — частный случай действия с `action_type ∈ {first_deposit, repeat_deposit}`. |
| FD / RD | Первый депозит (First Deposit) / повторный депозит (Repeat Deposit) клиента. |
| Лид | Потенциальный клиент, пришедший по каналу; фиксируется как действие с `action_type = lead`, необязательно привязанное к ID игрока. |
| Игрок / ID игрока | Идентификатор клиента в партнёрской платформе, к которому привязана цепочка его действий (регистрация → FD → RD). Отдельная сущность от «клиента» v0.1 (`client_ref` в депозите) — v0.2 хранит его как поле действия, без отдельной таблицы игроков (см. §11.6, открытый вопрос). |
| Канал | Источник трафика (рекламная кампания/паблишер), которым помечается действие. Принадлежит группе каналов и одной партнёрской платформе. |
| Группа каналов | Географическая или тематическая группировка каналов (например, «MENA»); используется как срез в лидербордах и отчётах. |
| Партнёрская платформа (провайдер) | Конкретный внешний сервис (PocketOption, Binolla и т.п.), с которого поступают действия через свой адаптер. Проект поддерживает несколько платформ одновременно — см. §11.4. |
| Предупреждение (warning) | Автоматическая пометка о расхождении между ручным вводом и данными партнёрки при сопоставлении (например, коррекция даты регистрации задним числом). |
| Тимлид | Руководитель группы менеджеров, видит статистику и рейтинг своей команды. |
| Аналитик | Роль только на чтение: статистика, лидерборды и конструктор отчётов по всей организации, без права вносить действия или что-либо согласовывать. |
| Sub-ID / метка | Идентификатор, которым помечается трафик конкретного канала/менеджера в партнёрке, чтобы действие можно было автоматически приписать каналу и менеджеру. |
| Топ / рейтинг / лидерборд | Упорядоченный список менеджеров по одной из метрик эффективности (касса, выручка на лид, конверсии — см. §11.2) за выбранный период. |
| MVP | Минимальная версия продукта, закрывающая ключевой сценарий учёта без второстепенных функций. |

## 3. Роли и права доступа

Права проверяются по роли пользователя в таблице `users`, а не по факту знания команды бота.

| Действие | Менеджер | Тимлид | Админ | Собственник | Аналитик |
|---|---|---|---|---|---|
| Просмотр своей статистики | ✓ | ✓ | ✓ | — | — |
| Ручной ввод действия (регистрация/FD/RD/лид) | свои | своя команда | любые | — | — |
| Своё место в топе команды | ✓ | ✓ | ✓ | — | — |
| Топ своей команды целиком | — | ✓ | ✓ | ✓ | ✓ |
| Топ по всей компании | — | — | ✓ | ✓ | ✓ |
| Запрос правки / удаления действия | ✓ | ✓ | ✓ | — | — |
| Согласование правок | — | своя команда | все | — | — |
| Установка целей (KPI) | — | своя команда | все | — | — |
| Управление пользователями и ролями | — | — | ✓ | — | — |
| Управление каналами / группами каналов | — | — | ✓ | — | — |
| Настройка интеграции с партнёрками | — | — | ✓ | — | — |
| Экспорт отчётов | — | команда | всё | всё | всё |
| Конструктор отчётов | — | своя команда | всё | — | всё |
| Просмотр аудит-лога | — | команда | всё | — | — |

Собственник имеет доступ только на чтение агрегированной аналитики и не может редактировать данные — это осознанное ограничение, а не недоработка. Аналитик аналогично доступен только на чтение, но шире собственника: видит детальные отчёты и конструктор отчётов, а не только агрегаты.

## 4. Функциональные требования

### 4.1 Учёт действий МОП
- Действие — регистрация, первый депозит (FD), повторный депозит (RD), лид или вывод (withdrawal). Депозит v0.1 = действие с `action_type ∈ {first_deposit, repeat_deposit}` и заполненной суммой.
- Ручной ввод менеджером через Mini App/бота: тип действия, ID игрока, канал, сумма (для FD/RD/withdrawal), при необходимости комментарий.
- Автоматический приём через вебхук или опрос от партнёрской программы — см. 4.5. Один и тот же обработчик обслуживает все подключённые платформы.
- Дедупликация: действие из партнёрки и действие, внесённое вручную, не должны задваиваться в статистике. Сопоставление — по `external_id` от партнёрки, если он есть; иначе по совпадению ID игрока, типа действия и суммы в окне ±N минут. Такие случаи получают статус «требует проверки» и не попадают в рейтинг автоматически.
- Каждое действие хранит источник (`manual` / `affiliate_api`) и, если применимо, `warnings` — список автоматических коррекций при сопоставлении с данными партнёрки (например, «дата регистрации скорректирована по данным ПП: 2026-09-04 → 2026-09-03»), видимых в списке действий.
- Список действий фильтруется по ID записи, диапазону дат, **ID игрока (поиск по трейдеру)**, типу действия, диапазону суммы, каналу, группе каналов, партнёрской платформе, МОП и его тимлиду.

**Зарплата и касса.** Каждый менеджер имеет две отдельные комиссионные ставки — `fd_commission_rate` (по умолчанию 10%) и `rd_commission_rate` (по умолчанию 7%), настраиваются админом индивидуально. За период:
- **Зарплата** = `сумма FD × fd_commission_rate / 100 + сумма RD × rd_commission_rate / 100`. Вывод (withdrawal) зарплату не уменьшает — это не отзыв комиссии, а фиксация факта вывода средств игроком.
- **Касса** = `сумма FD + сумма RD − сумма withdrawal` за период — отдельная от зарплаты метрика, показывает чистый денежный поток, закреплённый за сотрудником (соответствует метрике «Касса (FD+RD)» лидерборда, §4.9).
- Оба значения выводятся в личной статистике менеджера наравне с суммой/местом в рейтинге.

### 4.2 Статистика и топ сотрудников
- Рейтинг по сумме и по количеству депозитов (FD+RD) за гибкий период: день, неделя, месяц, произвольный диапазон.
- Сравнение с предыдущим периодом — рост или падение в процентах.
- Топ команды целиком — для тимлида, админа и аналитика; топ по компании — для админа, собственника и аналитика.
- Личная статистика менеджера с историей по дням, включая своё место в рейтинге команды (например, «3 место из 8») — без доступа к детальным цифрам коллег.
- Расширенные лидерборды с несколькими метриками и приватностью соседних позиций — см. §11.2.

### 4.3 Цели и KPI
- Назначение плана — целевой суммы депозитов — на менеджера или на команду на период.
- Прогресс-бар выполнения плана, доступный менеджеру и его тимлиду.
- Мягкая пометка в интерфейсе, если менеджер отстаёт от плана к середине периода, — без лишних уведомлений, чтобы не создавать шум.

### 4.4 Уведомления
- Менеджеру — о зачислении нового депозита на его счёт.
- Тимлиду — о крупной сделке в команде, порог настраивается.
- Админу и тимлиду — о депозите со статусом «требует проверки».
- Периодическая сводка (день/неделя) — тимлидам и админу, рассылается планировщиком.

### 4.5 Интеграция с партнёрскими программами
- Единый интерфейс адаптера (получение статистики и приём вебхуков), не завязанный на конкретного провайдера. Каждая партнёрская платформа регистрируется в системе (`platforms`) со своим ключом адаптера — систему можно подключить к нескольким платформам одновременно (например, PocketOption и Binolla параллельно), без изменения остального кода.
- Каждый канал (`channels`) принадлежит ровно одной платформе — так входящее событие от конкретного провайдера сразу понятно, к какому каналу и, через него, к какому МОП относится.
- Входящие события сначала попадают в промежуточную таблицу сырых событий и только после сопоставления с каналом/МОП по sub-ID/метке превращаются в действие.
- Вебхук-эндпоинт параметризован платформой (`/webhooks/affiliate/{platform_slug}`), у каждой платформы свой секрет для проверки подписи.
- Ключевой открытый вопрос — какие именно платформы подключаются первыми и умеют ли они метить трафик по каналу/менеджеру. См. раздел 9.

### 4.6 Административные функции
- Добавление и блокировка менеджеров, назначение роли (включая смену роли и команды у уже существующего пользователя по его Telegram ID) и тимлида.
- Формирование команд, назначение тимлида команде.
- Управление партнёрскими платформами: добавление платформы, ключи доступа, включение/выключение.
- Управление каналами и группами каналов: создание канала, привязка к платформе и группе каналов.
- Настройка порогов уведомлений.
- Просмотр аудит-лога изменений.

### 4.7 Экспорт отчётов
- Выгрузка статистики за период в Excel — по менеджеру, по команде, по компании.
- Экспорт доступен по команде бота и одной кнопкой из Mini App.

### 4.8 Журнал изменений (аудит)
- Любое изменение или удаление действия пишется в неизменяемый лог: кто, когда, что было и что стало.
- Правка чужого действия идёт через запрос на согласование — менеджер просит правку, тимлид или админ подтверждает, — а не через тихую перезапись.

### 4.9 Лидерборды
- Несколько видов метрик: **касса** (сумма FD+RD за период), **выручка FD на лид** (сумма FD, делённая на количество лидов за тот же период — эффективность канала/МОП), **конверсия LEAD→FD** (доля лидов, дошедших до первого депозита), **конверсия FD→RD** (доля первых депозитов, за которыми последовал хотя бы один повторный). Точные формулы и период агрегации по когорте/дате события — открытый вопрос, см. §11.2.
- Период агрегации переключается между «по месяцам» и «по неделям»; внутри — вкладки по месяцу/неделе.
- Срез по группе каналов (например, «MENA») отдельной вкладкой; вкладка «--» — без группировки/по всем.
- Приватность: полностью виден топ-3 (с иконками мест) и позиция самого пользователя с ближайшими соседями; промежуточные позиции скрываются строкой «Позиции N–M скрыты» для ролей менеджер/тимлид. Админ и аналитик видят лидерборд целиком без скрытия.
- Для каждой видимой строки — дельта «догнать следующего» (сколько не хватает до места выше) и «опережение предыдущего» (отрыв от места ниже).
- Собственная строка пользователя подсвечена и помечена бейджем «Вы».

### 4.10 Конструктор отчётов
- Доступен админу и аналитику по всей организации, тимлиду — в пределах своей команды.
- Настраиваемые: диапазон дат, фильтры (МОП, канал, группа каналов), набор колонок-агрегатов (количество лидов, REG, FD, сумма FD, RD, сумма RD и т.п.) и группировка (по МОП, по месяцу, по группе каналов).
- Результат — разворачиваемая таблица (группа → детализация по вложенным строкам), с сортировкой по колонке.
- Точный набор доступных полей/агрегаций и способ сохранения пользовательских шаблонов отчёта — открытый вопрос, см. §11.2.

## 5. Архитектура и стек

Стек продолжает уже освоенную связку — aiogram и Railway — с добавлением FastAPI как единой точки для вебхуков и REST, и PostgreSQL вместо SQLite: конкурентная запись действий от нескольких менеджеров и агрегирующие запросы для топа на нём не превращаются в проблему при росте данных. Mini App — основной интерфейс для всех ролей (не только владельца/админа), бот-команды остаются как более простой резервный канал.

| Компонент | Технология | Роль |
|---|---|---|
| Бот | aiogram 3 (Python) | Резервные команды, уведомления, запуск Mini App. |
| Mini App | Telegram Web App (статика + REST) | Основной интерфейс всех ролей: действия, лидерборды, конструктор отчётов, администрирование. |
| Backend | FastAPI | REST для Mini App/бота, приём вебхуков Telegram и партнёрских платформ, бизнес-логика. |
| База данных | PostgreSQL | Пользователи, действия МОП, каналы/платформы, цели, аудит-лог. |
| Планировщик | APScheduler → Celery + Redis | Сводки, опрос партнёрок, пересчёт агрегатов; рост — при увеличении объёма задач. |
| Хостинг | Railway | Бот, backend и PostgreSQL — отдельными сервисами. |

Поток данных:

```
Telegram (менеджер/тимлид/админ/владелец/аналитик)
   |  Mini App (WebView) + команды бота
   v
aiogram Bot (polling)              FastAPI Backend (REST + webhooks + планировщик) <---> PostgreSQL
                                          ^                                  ^
                    вебхук/опрос, per-platform adapter                REST /stats, /actions, /reports
                    Партнёрские платформы (N штук: PocketOption, Binolla, ...)
```

Реестр адаптеров (`backend/affiliate/registry.py`, план) сопоставляет `platforms.adapter_key` конкретной реализации `AffiliateAdapter` — подключение новой партнёрки сводится к (1) реализовать адаптер, (2) зарегистрировать его по ключу, (3) создать запись в `platforms` через админку. Остальной код (webhook-роут, промежуточная таблица, сопоставление, статистика) провайдера не знает.

## 7. Нефункциональные требования

### 7.1 Безопасность
- Вебхуки от партнёрки подписываются секретом (HMAC) и проверяются на бэкенде перед обработкой.
- Секреты и ключи хранятся в переменных окружения Railway, не в коде и не в репозитории.
- Доступ к каждой команде бота проверяется по `telegram_id` из таблицы `users`, а не по факту знания команды.

### 7.2 Масштабируемость
- `org_id` заложен во все ключевые таблицы с первого дня — подключение второй организации не требует миграции схемы.
- Переход бота с long polling на webhook-режим — вопрос конфигурации, а не переписывания хэндлеров.
- При росте объёма действий — партиционирование таблицы `mop_actions` по дате и составные индексы по (`org_id`, `mop_id`, `created_at`) и (`org_id`, `channel_id`, `created_at`).
- Фоновые задачи стартуют на APScheduler; путь роста — Celery с Redis, если объём и параллелизм задач вырастут.

### 7.3 Целостность данных
- Уникальный индекс по (`org_id`, `external_id`) в таблице `mop_actions` исключает задвоение на уровне БД, а не только в коде.
- Аудит-лог действий неизменяем — записи не редактируются и не удаляются.
- Правка чужого действия проходит через согласование, а не прямую перезапись.

### 7.4 Эксплуатация
- Ежедневные бэкапы PostgreSQL средствами Railway, с периодической проверкой, что восстановление действительно работает.
- Логирование ошибок бота и backend; отдельный алерт при сбое обработки вебхука от партнёрской платформы — иначе потеря действия останется незамеченной.
- Агрегирующие запросы для топа, лидербордов и конструктора отчётов — не дольше 1-2 секунд при нескольких тысячах действий; при необходимости — кэширование расчёта топа с коротким TTL.

## 9. Открытые вопросы

- **Какие партнёрские платформы подключаются первыми (например, Binolla)?** Есть ли у них API/вебхуки и можно ли пометить трафик по каналу/менеджеру. От ответа зависит архитектура §4.5 для конкретного адаптера — сам реестр под несколько платформ уже не зависит от выбора (см. §11.4).
- **Нужна ли многовалютность?** Если действия бывают в разных валютах или крипте — понадобится хранить курс на момент действия, а не только сумму.
- **Нужно ли подтверждение действия перед тем, как оно попадёт в статистику?** Например, одобрение тимлидом — или система доверяет источнику (менеджеру / партнёрке) сразу.
- **`org_id` — это чисто задел на будущее, или несколько организаций реально появятся?** Мульти-проектность (несколько изолированных организаций на один Telegram-аккаунт с разными ролями в каждой) сознательно отложена в v0.2 — см. §11.5.
- **Какая сумма считается «крупной сделкой» для уведомления тимлида?** Нужен конкретный порог, иначе уведомление либо молчит, либо спамит.
- **Точные формулы лидерборд-метрик и состав конструктора отчётов** — см. §11.2.
- **Нужна ли отдельная сущность «Игрок»** (лайфтайм-профиль клиента поверх цепочки его действий) или достаточно `player_id` как текстового поля на каждом действии — см. §11.6.

## 11. Ревизия v0.2 — обобщение модели и мульти-партнёрка

Основание: разбор образца интерфейса стороннего ERP-продукта (рабочее название источника — «Jarvis Fin ERP»), предоставленного как ориентир по функциональности и UX. Экраны-источники: список проектов, карточка проекта с блоками «Учёт данных»/«Отчётность», фильтруемый список действий МОП, лидерборд с несколькими метриками, административный сводный отчёт с ролями `[ADMIN | MOP | MOP_LEAD | ANALYTIC]`.

### 11.1 Соответствие терминов источника нашей модели

| Термин источника | Наш термин |
|---|---|
| МОП | Менеджер |
| МОП TeamLead | Тимлид |
| ANALYTIC | Аналитик (новая роль, см. §3) |
| Действие МОП (REG / FD / RD / лиды) | `mop_actions.action_type` |
| Партнёрская сеть / Партнёрская Платформа | `platforms` |
| Канал | `channels` |
| Группа каналов (например, «MENA») | `channel_groups` |
| ID игрока | `mop_actions.player_id` |
| Предупреждения (в списке действий) | `mop_actions.warnings` |
| Лидерборд | Расширенный топ, §4.9 |
| МОП Cashflow (сводный отчёт) | Конструктор отчётов, §4.10 |

### 11.2 Метрики лидерборда и конструктора отчётов — требуют уточнения на реальных данных

Из скриншотов видна структура, но не всегда точная формула:
- **Касса (FD+RD)** — по подписи источника «отчёт по дате внесения FD/RD (Cashflow-метод)» — суммируются действия, у которых `created_at` (дата фактического зачисления) попадает в период, независимо от даты регистрации игрока.
- **Выручка FD на лид** — по подписи «построен по данным МОП, до 10 числа нового месяца (когортный метод)» — похоже на когортный расчёт: лиды когорты периода делятся на FD той же когорты, а не просто FD/лиды за один и тот же календарный отрезок. Нужно подтвердить точную формулу и правило переноса когорты (до 10 числа) на реальном примере.
- **Конверсия LEAD→FD, FD→RD** — предполагаемая формула: доля уникальных `player_id`, дошедших до следующего шага воронки, за период/когорту. Требует подтверждения аналогично предыдущему пункту.

Пока формулы не подтверждены, реализация метрик — по когортному методу «как источник заявляет в подписях», с явным указанием метода расчёта в интерфейсе (как в скриншотах).

### 11.3 Приватность позиций в лидерборде — рабочее правило

Скриншоты показывают: полностью видны топ-3, дальше — видна только позиция самого пользователя и её ближайшее окружение, промежуток скрыт строкой «Позиции N–M скрыты». Рабочее правило до уточнения: видимы топ-3 + позиция пользователя ± 1 строка; всё остальное — под общим счётчиком скрытых позиций. Админ/аналитик видят список целиком без скрытия.

### 11.4 Реестр адаптеров под несколько партнёрских платформ

Ключевое требование пользователя: «легко интегрировать партнёрку уже после всей разработки, и несколько партнёрских программ (например, Binolla)». Решение:
- `platforms` — по записи на каждую подключённую партнёрку, с полем `adapter_key`.
- `backend/affiliate/registry.py` (план) — сопоставление `adapter_key → класс AffiliateAdapter`, регистрация новых адаптеров не требует правок в остальном коде (webhook-роуте, сопоставлении, статистике).
- Вебхук-роут параметризован платформой: `/webhooks/affiliate/{platform_slug}`, секрет проверки подписи — свой на платформу (`platforms.webhook_secret`), а не общий на всё приложение (было в v0.1).
- Добавление второй/третьей партнёрки — это (а) реализация нового адаптера, (б) запись в `platforms` через админку, без миграции схемы и без изменения существующих адаптеров.

### 11.5 Сознательно отложено: мульти-проектность

Экран «Мои проекты» на скриншотах подразумевает, что один Telegram-аккаунт может состоять в нескольких независимых организациях с разными ролями в каждой — это требует вынести роль/команду из `users` в отдельную таблицу членства (`org_memberships`) и добавить переключатель проекта в Mini App. По решению на текущей итерации — не делаем: `org_id`/`role`/`team_id` остаются полями `users`, один Telegram-аккаунт = одна роль в одной организации. Если понадобится — потребуется отдельная миграция авторизации, описанная здесь как задел.

### 11.6 Сознательно отложено: отдельная сущность «Игрок»

Источник, судя по всему, ведёт по каждому `player_id` профиль с историей (регистрация → FD → RD), но подтверждающих экранов такого профиля не было. Пока `player_id` — текстовое поле на `mop_actions`, без отдельной таблицы игроков. Если понадобится лайфтайм-карточка игрока (обязательства/статус/сумма LTV) — потребуется таблица `players` (уникальна по `org_id + platform_id + player_id`), не блокирует текущий объём.

### 11.7 Внешние интеграции по API-ключу (задел под сайт/Chatterfy)

Требование пользователя — сделать приложение «многоинтегрируемым», в том числе как backend позади внешнего сайта или платформы вроде Chatterfy, без привязки к Telegram-сессии:
- `api_keys` — токен на организацию, привязанный к конкретному `user_id` (сервисной учётной записи с нужной ролью — обычно `admin` или отдельный технический пользователь). Хранится только хэш ключа (`sha256`), сам ключ показывается один раз в момент создания.
- Запрос с заголовком `Authorization: Bearer <ключ>` аутентифицируется как этот `user_id` — все те же ролевые проверки (`require_role`), тот же REST API, что и у Mini App/бота, просто другой способ подтвердить личность.
- Управление ключами — только у админа/владельца: выпуск (`POST /api-keys`), список (`GET /api-keys`), отзыв (`POST /api-keys/{id}/revoke`).
- Никакой специфики Chatterfy пока не реализована — сам механизм ключей и есть тот самый «задел», после выбора конкретного API Chatterfy потребуется только отдельный адаптер или прямые вызовы REST с этим ключом, без изменения модели авторизации.
